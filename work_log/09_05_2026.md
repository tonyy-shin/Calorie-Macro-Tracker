# 09/05/2026

## Phase 3: Users and auth 

### Schema
- Created `users` table (`id`, `email UNIQUE`, `password`, `created_at`).
- Used `CREATE TABLE IF NOT EXISTS` rather than `DROP TABLE IF EXISTS` —
  the rerunability pattern from the gold scripts is wrong here. User rows
  can't be regenerated from a source dump the way pipeline tables can.

### Password hashing
- `bcrypt` in Python, not a DB side hashing function. Two reasons:
  hashing in SQL sends the plaintext password over the wire and into
  `pg_stat_activity` / query logs, and general purpose hashes 
   are built to be fast, which is exactly wrong for passwords.
  bcrypt's cost factor and per password salt are the point.
- Deliberate exception to the project's "logic lives in SQL, not Python"
  rule. That rule governs the pipeline; auth is app layer.

### src/python/auth.py
- `register_user(conn, email, password)` — hashes, inserts with
  `RETURNING id`, commits, returns the new id. Catches
  `psycopg.errors.UniqueViolation` on duplicate email and rolls back;
  without the rollback the connection stays poisoned and every later
  query fails with "current transaction is aborted."
- `verify_user(conn, email, password)` — fetches `(id, password)` by
  email, returns `None` if no row, otherwise `bcrypt.checkpw` and returns
  the id or `None`. Order matters: the hash has to come out of the DB
  before there's anything to compare against.
- All values parameterized, never fstrings. First point where user input
  decides what data someone can see.

### Verification
Five paths tested in the REPL, all correct:
| case | expected | got |
|---|---|---|
| register new | id | 1 |
| register duplicate | None | None |
| correct password | id | 1 |
| wrong password | None | None |
| unknown email | None | None |

The duplicate case also confirms the rollback works — the three calls
after it succeeded on the same connection.
